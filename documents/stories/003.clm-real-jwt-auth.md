# Story: CLM Real JWT Authentication

## 1. 개요 (Overview)
- **목표:** 하드코딩된 'demo-token-123'을 대체하는 실제 JWT(JSON Web Token) 기반 인증 시스템을 구현한다. 사용자는 로그인 프로세스를 통해 유효한 토큰을 발급받으며, 모든 API 요청은 이 토큰의 서명을 검증받아야 한다.

## 2. 페르소나 (Persona)
- **User:** 이메일과 비밀번호를 통해 시스템에 로그인하여 자신의 테넌트 권한에 맞는 토큰을 획득한다.

## 3. 인수 조건 (Acceptance Criteria)

### 시나리오 1: JWT 발급 (Login & Issue)
- [ ] **Given** 유저가 유효한 이메일과 비밀번호로 `POST /auth/login` 요청을 보낸다.
- [ ] **When** 백엔드에서 유저 정보를 검증하면
- [ ] **Then** `accessToken`을 포함한 JSON 응답을 반환한다.
- [ ] **And** 토큰의 페이로드에는 `userId`, `email`, `tenantId` 정보가 포함되어야 한다.

### 시나리오 2: JWT 검증 및 가드 연동
- [ ] **Given** 사용자가 API 요청 시 `Authorization: Bearer <JWT>` 헤더를 포함한다.
- [ ] **When** `TenantAuthGuard`가 요청을 가로채면
- [ ] **Then** 비밀키(Secret Key)를 사용하여 JWT의 유효성을 검증한다.
- [ ] **And** 유효하지 않은 토큰(만료, 위조 등)인 경우 `401 Unauthorized`를 반환한다.

### 시나리오 3: 테넌트 정보 자동 추출
- [ ] **When** 토큰 검증 성공 시
- [ ] **Then** 토큰 내부에 포함된 `tenantId`를 추출하여 `Request` 객체에 주입한다. (클라이언트가 명시적으로 헤더를 보내지 않아도 토큰에서 식별 가능하도록 고도화)

## 4. 아키텍처 및 제약사항 (Architecture Notes)
- **라이브러리:** `@nestjs/jwt`, `passport-jwt`
- **보안:** `process.env.JWT_SECRET`을 통해 비밀키 관리.
- **유연성:** `TenantAuthGuard`는 `x-tenant-id` 헤더가 없는 경우 토큰의 `tenantId`를 기본값으로 사용한다.
